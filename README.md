# NexaStream operator dashboard

## One common URL for all registered devices

After deploying both current services, sign in and read **One URL for every activated MAC**. It displays the actual TV service origin for **Stalker Server + MAC** mode and that origin plus `/c/index.html` for **MAG/STBEmu external Portal URL** mode. The shared link only appears if the TV service confirms `ENABLE_MAC_STALKER_PORTAL=true`; an existing Render service may require setting this environment variable manually and redeploying. Check the Portal URL returns the MAG page before trying it on the device. If `SUBSCRIBER_BASE_URL` specifies a custom domain, the shared links use that domain. These addresses do not change for each MAC; the active, unexpired account is chosen from the MAC that the device actually reports. More than one row with the same MAC blocks shared login even if one is suspended: review My Customers and clear the MAC on obsolete entries using **Edit MAC**, or repurpose an existing account. Never create another account just to troubleshoot and do not rotate private URLs for this flow. The older tokenized MAG, TV browser, and M3U links still exist and are separate.

**Warning:** MAC addresses are spoofable. Anyone who knows an active MAC can request this service's catalog and upstream playback URLs, and suspension cannot recall upstream links already issued. Import authorized playable live and movie streams separately; this dashboard manages access, not the catalog. Real STBEmu/TV protocol and codec support remains unverified; an app requiring Xtream username/password will not work with these URLs.

This **separate private-operator console** manages customer MAC addresses, expiry, activation/suspension, and replacement links on the already hosted TV API at `https://nexastream-tv.onrender.com`. It is not an IPTV player and does not host videos. Your existing dark admin UI is included. Customer data remains in the TV service's PostgreSQL database, not here.

## Deploy

In Render, choose **New → Blueprint**, connect `krishhathidara/iptv-Dashboard`, and review `render.yaml`. The TV service must already exist as `nexastream-tv` in the **same Render workspace**. The Blueprint now references that service's `ADMIN_API_KEY` for `TV_ADMIN_API_KEY` and its `RENDER_EXTERNAL_URL` for `TV_API_URL`; no key needs to be entered in the dashboard or copied to GitHub. During setup supply the one **secret** requested by the Blueprint:

1. `DASHBOARD_PASSWORD`: generate a random secret at least 32 characters long. This is what you type into the dashboard Sign in form; **do not enter the TV API key in that form**. Save the password in a password manager.

For an **existing** dashboard service, sync the updated Blueprint and confirm its `TV_ADMIN_API_KEY` is referencing the TV service's `ADMIN_API_KEY` and `TV_API_URL` points at the TV service. Render updates cross-service references on Blueprint sync, not immediately when the TV key changes. A dashboard created manually (not from this Blueprint) needs its Render environment updated instead. Do not remove the TV service's key: the public TV service refuses customer writes without it.

`DASHBOARD_SESSION_SECRET` is generated by Render. Render sets `RENDER_EXTERNAL_URL` for the new dashboard service, which the app uses for request-origin checks. If you use a custom domain, set `DASHBOARD_PUBLIC_URL` to its exact HTTPS origin in the dashboard service's Environment before signing in. Do not deploy this app as GitHub Pages, a static site, or on plain HTTP. Verify the deployment's `/health` endpoint returns `{"status":"ok"}` and open the **actual dashboard URL** from Render; pushing to GitHub alone does not create that URL. The TV service must remain live and reachable. This dashboard only permits same-origin cookie/CSRF protected customer actions; it does **not** accept your TV admin key in browser requests. Use HTTPS and protect your operator password. It has basic per-instance failed-login throttling, not enterprise authentication/MFA; use additional access control for production.

### If customers do not load

After deploying the TV service's database-readiness update, check the TV service's `/health`: `200` means the customer table responds; `503` means its database or subscriber table is unavailable. This check cannot validate the dashboard's configured TV URL or admin key. A database-unavailable response appears explicitly in this dashboard after both services are redeployed; the older generic server-error response still requires checking the TV service logs. If the TV PostgreSQL instance has expired, resolve that in Render before retrying: a code deployment does not restore an expired database or its customer records.

Sign in with the dashboard service's `DASHBOARD_PASSWORD`, **not** either API key. Sign in reports whether authentication worked separately from the TV customer connection. The New Customer and My Customers sections open after authentication even if the initial TV request fails; the message beside Create shows why saving is currently blocked. Use **Refresh** once the TV service is working. Customer creation and updates still require the TV service; never repeat a timed-out create before refreshing the list, because it may already have succeeded. A red **“TV service rejected the admin key”** message means your operator password *did* sign in, but the server-to-server `TV_ADMIN_API_KEY` does not match the TV service's `ADMIN_API_KEY`; entering that key in the password form cannot fix it.

In Render, check **both** services separately: the dashboard service Environment needs `TV_API_URL` set to the **actual** TV service HTTPS origin (no path), `TV_ADMIN_API_KEY` referencing the TV service's `ADMIN_API_KEY` (or manually matching it if the dashboard was not created by the Blueprint), and `DASHBOARD_PASSWORD` set to a separate 32+ character secret. Save environment changes and wait for redeployment. On the TV service, check **Logs** for errors from `/admin/subscribers`, its PostgreSQL database is available, and its `/health` endpoint responds. Once the TV database-readiness update is deployed, the TV health response checks access to the customer table, but not the dashboard's TV URL or admin key. If you see a key rejection, fix the key pair privately; if a timeout, wait for the sleeping service to wake and use Refresh; if a server error, inspect the TV service logs and database status. Never put real secrets in a support message or GitHub. Rotate any previously shared keys/passwords in Render before using real accounts.

## Create a customer and enter the portal URL on a TV

Sign in with `DASHBOARD_PASSWORD`. Enter the customer's name, the **MAG device MAC address** (six hexadecimal pairs, e.g. `AA:BB:CC:DD:EE:FF`), and duration. **Activate immediately** is checked by default; uncheck it if you want to activate the account later from My Customers. The dashboard shows **“Account created for …”** beside the Create button only after the TV service confirms the save. In **One URL for every activated MAC**, copy the shared Portal URL into a compatible MAG/STBEmu external-portal setting, or the shared Server address into a Stalker Server + MAC app. The separate private links generated for each account cannot be fetched again later; **Replace URLs** invalidates old private links but is not required for shared login. Older private MAG links have this shape:

```text
https://nexastream-tv.onrender.com/stalker/<unique-private-token>/c/index.html
```

`<unique-private-token>` is **not a literal value**. The dashboard URL and TV browser URL are **not** MAG portal URLs. Shared login intentionally allows access based on an active, unique, device-reported MAC alone; the private legacy portal additionally requires its link. The `TV browser URL` (`/watch/<token>`) is for TV web browsers; the `.m3u` link is for M3U-compatible players. Third-party Stalker apps or individual MAG firmware may not support this limited portal, so test on your physical box. The TV catalog starts empty unless you import authorized streams into the TV service separately; this dashboard manages **customers**, not channels.

**STBEmu Pro on Fire TV:** In Settings → Profiles → your profile → Portal settings, put the **shared MAG Portal URL shown at the top of the dashboard** into Portal URL. In the same profile's STB configuration, find its **emulated MAC address**; that is the MAC to record for this customer, not necessarily the Fire TV hardware address. After editing the MAC or URL, reload the profile. The TV service's custom MAG portal requires both updated services to be deployed and separately imported licensed live streams and direct movie streams to display content. The dashboard manages customer access only; it cannot populate a movie or live TV catalog. Do not use the TV browser or M3U URLs in STBEmu. STBEmu compatibility on a physical Fire TV has not been verified, so do not promise playback based solely on a working local API test.

**Other apps showing Server / Portal options:** A `/c/index.html` URL is a MAG web page, **not** a Server URL. For **Server + MAC**, use the shared TV origin shown at the top of the dashboard (not the dashboard origin); its Stalker API accepts `portal.php` and `server/load.php` below that origin. Your active, unexpired account must have the exact MAC reported by the app. If you already created the account, **do not create another one**: in *My Customers → Connect an existing customer*, enter the MAC reported by the app to check its saved status against the customer list. An original private MAG link can optionally be verified in that form, without changing the account; it is not required for shared login. A missing/duplicate MAC, wrong login mode, missing deployment or incompatible player can all cause connection errors. The shared MAC-only entry point is opt-in in the app configuration but enabled in this repository's TV Render Blueprint; check the actual TV service environment and dashboard status. MACs can be spoofed. Do not create another customer until My Customers loads; a failed refresh does not roll back a successful create. Do not paste private links into screenshots or logs.

If the TV app asks for an **Xtream username and password** instead of Server + MAC or an external portal URL, this service does not issue Xtream credentials. Do not type the dashboard operator password or either admin API key into a TV app. A generic “authentication failed” message may mean the wrong app mode, a mismatched device-reported MAC, an inactive or expired account, an invalidated/incorrect private URL, or an unsupported device protocol; it does not establish which one occurred. Check the existing row and the app's exact configuration privately before changing account settings.

**Existing URL verification (requires both updated services):** The form now sends the saved private MAG URL to the authenticated dashboard over the same-origin HTTPS connection. The dashboard checks the URL shape, then sends only the token and entered MAC to the configured TV service with its server-side admin key. The TV service returns the URL's actual customer, configured portal origin, active status, expiry and whether the MAC matches. The dashboard rejects a URL whose origin differs from the service's configured portal origin (including deployments with a custom TV domain). A verified Server address appears only when that specific account is active, unexpired and its saved MAC matches. The check is read-only and does not create, rotate or update an account; it cannot prove that the TV app reports that MAC or speaks this custom Stalker protocol. Earlier dashboard versions only checked the MAC in the customer list and derived the Server URL locally; those checks did **not** verify ownership of the URL. Treat saved URLs as private credentials.

Suspending an account stops future portal/API/playlist requests, not an upstream stream URL the TV has already received. A reported MAC can be spoofed; do not assume this identifies hardware. Only use video streams you are licensed to distribute. The TV host's free Render database expires after 30 days unless upgraded; free web services sleep when idle, which can disrupt TV access. Do not use free trial resources for paying customers.

## Local checks

Install dependencies in a virtual environment and run `python -m pytest -q` and (with Node.js available) `node --test tests/dashboard_ui.test.js`. For local use set the values from `.env.example` in your shell environment; the app intentionally fails startup without a TV key and session secret. **Only for private loopback testing:** set `DASHBOARD_PASSWORDLESS_LOCAL=true`, `DASHBOARD_PUBLIC_URL=http://127.0.0.1:8000`, leave `DASHBOARD_PASSWORD` unset, and run the dashboard bound to `127.0.0.1` (`python -m uvicorn main:app --host 127.0.0.1 --port 8000`). The sign-in form is hidden and the local browser gets a session automatically. The TV key is still required server-side and `TV_API_URL` must be the actual HTTPS TV service origin; this mode is blocked on Render and non-loopback hosts. Never commit real secrets.
